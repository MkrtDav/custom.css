Common rules and mechanics for the ADM protocols

The rules every bet, game session and account movement follows when it is exchanged in real time with ADM's central system (Sogei): order of steps, settlement, retries, integrity checks and accounting.

Use with the task CHG-375321. The task is the requirement. This kit adds reference detail for building and testing it: ADM rules with their sources, flows, messages and checks. If the kit and the task differ, the task prevails; if the task and ADM's protocol differ, the protocol prevails.

At a glance

  • ADM must know first. Where the game type requires it, the event, race, schedule or game session is opened at ADM before the first bet. No bet is accepted before that.
  • ADM answers, then we debit. A bet is accepted and the stake debited only after the central system returns its unique bet code. A negative reply means the bet is refused.
  • No cancel after the code. Refunds for cancelled events, result corrections and odds errors go through ADM routes only.
  • Winnings in two steps, within one hour. The win or refund goes to ADM through the game protocol, then the credit goes to the gaming account register (PACG). The player is credited only after the PACG positive reply.
  • What the player sees. Every bet screen shows the ADM unique code, the amount debited, the gaming account code and the account holder's tax code.
  • Scope. Four ADM game systems: fixed-odds betting (PSQF), virtual betting (PSV), horse-race fixed-odds betting (PSIP) and skill, card and fixed-odds chance games (PGDA). The gaming account register (PACG) serves all of them.

Rules

A. Validate first, then move money

Product (protocol)What must exist at ADM before the first bet
Sports betting (PSQF)The event exists at ADM, taken from ADM's event calendar or created with the event creation message. For markets with dynamic outcome lists, the outcome list is sent before betting on that market.
Horse racing (PSIP)Bets only on races in ADM's official daily schedule. Complementary events (antepost races, multi-race events) are created at ADM before they are sold.
Virtual sports (PSV)The schedule and each virtual event, multi-event or tournament are opened at ADM before they are sold.
Casino (PGDA)A game session is opened at ADM and accepted before the first participation message (220); in the skill-tournament mode enrolments are taken on the concessionaire's own channels without a message to ADM. RNG and table games (mode 3): message 400. Cash card games (mode 4): 600. Skill games: 200 opens the session and 250 validates it just before play. If ADM returns an error, no player is registered and nothing else is sent. Instant games: one message per play (510), no session.
Account register (PACG)Every message that moves an account carries the balance and bonus share. Needed by every product (login sub-registration, credits).
  1. Send each bet or game participation to the central system through the protocol of its game type. Accept the bet and debit the stake only after the central system returns the unique bet or participation code. If the reply is negative, refuse the bet and tell the player. ODV guidelines 2025 par. 2.1.1.1
  2. The player's account moves only after the platform has received and stored the identifier from the central system. ODV guidelines 2025 par. 2.1.1.1
  3. Every message that moves an account carries the account balance with the remaining bonus share. For a stake paid partly with bonus, the cash and bonus parts are declared in the game-protocol message and the bonus share is carried in the balance. A bonus balance cannot be withdrawn until it has been converted into withdrawable money (PACG 6.6 type 3). Guidelines 2.9.16, 2.9.16.1; Gaming account contract art. 5 c. 11; PACG 3.3 par. 6.6
  4. The balance declared in a message is the balance after the operation. Example in PSQF, PSV and PSIP: balance 100 with bonus 20 becomes 70 with bonus 10 after a sale of 30. PSQF 5.2 par. 13.50 SALDO_CONTO, 13.54, 13.55; PSV par. 13.11-13.12; PACG 3.3 par. 6.3
  5. Every check that could lead to a rejection (limits, self-exclusion, risk, liability, balance) runs before the bet is sent, and the stake is reserved before sending, so the debit cannot fail after the code arrives. platform design rule

B. Settlement

  1. Settlement has two steps, both in real time. Step 1: send the win, refund, void or adjustment to the central system through the game protocol; store the positive reply with the amount and update the bet or session. Step 2: send the credit or reversal to the gaming account register (PACG 6.8 or 6.36 credit, 6.9 reversal) with the balance and bonus share. Credit the player's account only after the PACG positive reply. Guidelines 2.1.2.1, 2.1.3.1
  2. Winnings and refunds are booked and made available to the player no later than one hour after the official certification of the event that creates the win or refund. For a sum the player asks to be released, the hour runs from the request. For session games it runs from leaving the game session (for card tournaments, from the closing of the session). The clock stops when the win or refund is booked on the gaming account. A slow step 1 does not extend it. Concession agreement art. 11 c. 6 (a); ODV guidelines 2025 par. 2.9.17, 2.9.17.1; Technical Rules Part 2 ch. 9
  3. Once the central system has returned the bet code the bet is accepted and the platform cannot void it. The PSQF cancel message is refused for remote bets (return code 4004). Later changes go only through ADM routes: refund when the event is cancelled, result correction through the protocol's messages, odds errors through ADM's odds-error procedure. PSQF 8.4, 14.30
  4. Bets placed before a self-exclusion, limit breach or suspension stay valid and are settled normally; activities already started are always completed after a self-exclusion or limit breach. ODV guidelines 2025 par. 2.9.4, 2.9.1.1

C. Bet screens

  1. Bet detail and bet history screens show at least: the ADM unique code, the amount debited, the gaming account code and the account holder's tax code (codice fiscale). The ADM unique code is the only bet identifier shown; other detail may be added. Technical Rules Part 1 par. 1.1 pt 11 b; ODV guidelines 2025 par. 2.3.2, 2.3.2.1
  2. Every page reachable after identification, in particular the pages with balance, movements and bet detail, shows the concession number, the concessionaire's company name, the gaming account code and the player's tax code, also on printouts. The text mentions no masking. Gaming account contract art. 5 c. 19

D. Link and message security

  1. Link to the central system: a dedicated LAN-to-LAN line (up to 100 Mbps, port on a layer 3 switch) or a VPN over the internet with the technology ADM and Sogei specify. The link is redundant, the connections are registered in Netbet's name, and the network is used only for gaming data and is monitored. An SPC link is allowed only for horse betting and only inside Italy. Technical Rules Part 2 ch. 8 p. 19-20; ODV guidelines 2025 par. 2.8.2
  2. The gaming account system exchanges data with the central system only under Netbet's concession and over Netbet's own direct link. Technical rules Part 1 ch. 2 p. 8; Part 1 par. 1.1(3); Part 2 ch. 2, 5, 8
  3. Message-level security is as each protocol defines it. PACG: WS-Security username token plus digital signature (the username is the Common Name of the concessionaire's signing certificate; the body is signed with the concessionaire's private key; encryption applies only to the messages that list "Cifratura", 6.1 and 6.29). Betting protocols: a digital-signature attribute (public keys exchanged in PEM through the key-exchange service 8002:1). PGDA: PKCS#7. Certificates are issued to Netbet. PACG 3.3 par. 2 p. 16; PSQF 5.2 par. 10.1 p. 176-177
  4. When the concessionaire uses third parties, it remains solely responsible towards ADM and players for the services they provide. Concession agreement art. 19 c. 6
  5. Proprietary protocols between internal components need integrity and confidentiality equivalent to the ADM link. Between site or app and player: secure protocols (guideline 2.7.8.1), data encrypted in transit and at rest (Technical Rules Part 2 ch. 1). ADM fixes no algorithm or key length for these. Technical Rules Part 2 ch. 8 p. 19, ch. 1 p. 10; ODV guidelines 2025 par. 2.7.8.1

E. Interfaces, time, retries, integrity

  1. One modular, independent interface per protocol and one per game platform, each identifiable by the verification body. Guidelines 2.5.1
  2. All components use UTC as the time reference; logs and message timestamps refer to a UTC source. Betting protocol timestamps are UTC (TIME_STAMP_UTC), PACG V3 uses DataOraUTC for its UTC fields (plain Data and Ora fields keep the older convention: CET with automatic summer time), and PGDA systems are synchronised to UTC. Some PGDA fields are defined by the Italian date and follow the protocol. ODV guidelines 2025 par. 2.1.5, 2.1.5.1; PGDA 3.1.0 par. 4.1
  3. Never debit or credit without a positive reply. A resend uses the same transaction ID and an unchanged request. Retry intervals are fixed per protocol (table in section 4). PSQF par. 2 p. 18; PACG par. 2.1 p. 17; PGDA par. 7.2 p. 169
  4. Automated software-integrity checks send message digests to ADM through each protocol: PSQF 8004:2, PSV 9500:2, PSIP 3900:2, PGDA 833 and PACG 6.7. The check runs at least daily and again after any corrective patch or bug fix. It stores timestamp, component, result and outcome of the send. A failed check is recorded and the component may keep running for 15 calendar days; if the check fails again after 15 days the component is blocked. The messages are built for every protocol in every connection mode. ODV guidelines 2025 par. 2.1.13, 2.1.13.1; PACG 3.3 par. 6.7 p. 197-199
  5. Audit logs record all operator and administrator actions on every component (date, time, type of operation, identity) and are protected against alteration and unauthorised access. ODV guidelines 2025 par. 2.1.11.1
  6. Stored information is available to ADM in real time for the last six months, and accounting information for the last two years; afterwards it is kept for at least five more years with integrity, readability and access. The gaming account contract adds ten years for the detailed account movements and bets. ODV guidelines 2025 par. 2.1.16, 2.1.16.1; Gaming account contract art. 5 c. 20
  7. Each protocol is tested with Sogei (communication checks v1.2.1) before certification. Start of collection depends on a positive technical-functional verification. ADM sets the verification date for each game type and communicates it at least five days ahead; it records a report and can set corrective steps and a new date. Concession agreement art. 19 c. 2-5

F. Accounting and reconciliation

  1. Reconcile per game type with ADM's accounting replies: PSQF 8000:1, PSV 9200:1, PSIP 3500:1, PGDA 800. PSIP codes 16, 40 and 41 come with game type 0; 40 and 41 only for holders of the new concession; 16 is not a tax line. ADM's central system determines the single tax from the data it receives. Technical Rules Part 1 par. 1
  2. PSQF 8000:1 is requested by year, month and day of competence and returns amounts, counts and rates by tax band and accounting reason (11 single tax, 40 State, 41 Region of Sicily). Return code 1530 means the data for that day are not processed yet, so a daily request is repeated. PSQF 5.2 par. 9.1 p. 156-158, par. 14.6 p. 246-247

G. Game systems

  1. ADM defines seven game systems: (1) fixed-odds sports and non-sports betting; (2) simulated events; (3) horse fixed-odds and totalizator; (4) pool betting and non-horse totalizator; (5) national horse games and horse pools; (6) skill games including card games, fixed-odds chance games and remote bingo; (7) other virtual or digital games. Netbet's scope is systems 1, 2, 3 and 6 (PSQF, PSV, PSIP, PGDA); bingo, pool betting, national horse games and betting exchange are out of scope. Offer in Italy only products that map to these systems. ODV guidelines 2025 par. 2.2.1

H. Edge cases

  1. No reply from the central system after a bet is sent: the bet is not accepted and nothing is debited. Resend with the same transaction ID and recover the outcome with the protocol's own query and resend rules before telling the player the final result. PSQF par. 2 p. 18
  2. Step 1 accepted, PACG credit refused or timed out: the account is not credited. Retry the credit with the same transaction ID until a definitive reply; the one-hour limit still applies. Guidelines 2.1.3.1, 2.9.17; PACG 2.1
  3. ADM link or game system failure: if the central system answers with an error, the player is told and play does not start or continue. For casino and card games (PGDA), if a malfunction stops play and it cannot be resumed or restored from the last stored data, bets are refunded in full at the concessionaire's cost and ADM and the player are informed; open virtual events are cancelled with a refund. ODV guidelines 2025 par. 2.1.1.1, 4.1.1, 4.2.1, 4.2.1.1

Positive: debits the reserved stake, declares the balance and bonus share (PACG), shows the ADM code and amount debited. Negative: releases the reservation, nothing is debited, the player is told.

0

1

No reply from ADM

The platform resends the bet with the same transaction ID (2 s, 4 s, then every 4 s). The stake stays reserved and the player sees an awaiting state. When a reply arrives, the stored original reply carries the bet code and the stake is debited.

Resend of a transaction already stored

PSQF, PSV, PSIPNo "already processed" code. The server returns the stored original reply without processing again, for the last transaction only (a resend returns the stored reply only if no other transaction came in between). The transaction identifier is 8 bytes and must differ between two consecutive transactions.
PACGReturn code 1027, "transaction ID refers to a request already processed".
PGDA1003, "transaction code refers to a different request already made"; 1070, message already sent; and 1760, a generic duplicate-record code. The list in PGDA is not complete.

Transport and header

The betting protocols are half-duplex request and reply exchanges, not connection-oriented; the reply address is in the IP_RISP attribute. In the PSQF, PSV and PSIP header the field versione is 2 when the connectivity provider id (fsc) is used and 3 when a service-provider concessionaire id (cfs) is used. The exchange with the central system goes through a CFS only when the concessionaire's system contains the game system of a service-provider concessionaire; in all other cases the concessionaire exchanges data directly. Keep the header version and the provider field configurable. {src: PSQF 5.2 intro p. 16-17, par. 4.1 p. 22; PSV par. 4.1; PSIP par. 4.1; ODV guidelines 2025 par. 2.8.1; Concession agreement art. 16 c. 1}
