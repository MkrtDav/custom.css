Inactivity time-out and end of session

How the Italian site and apps end a user session: the inactivity time-out, the four end causes, forced closure, game sessions, the account-register disconnection (PACG 6.32) and the session-end record.

Use with the task CHG-375441. The task is the requirement. This kit adds reference detail for building and testing it: ADM rules with their sources, flows, messages and checks. If the kit and the task differ, the task prevails; if the task and ADM's protocol differ, the protocol prevails.

1. At a glance

  • Time-out. Default at most 20 minutes after login. At the limit gaming and account management are blocked and the player is logged out.
  • Player setting. The player can set another value, always below 60 minutes (highest 59). Default and range are settings, not hard-coded.
  • Inactivity means no interaction with the graphical interface of the site or app and no open game session. A player in an open casino game session is not inactive.
  • Four ways a session ends: logout, time-out, a documented condition set by the concessionaire, forced closure of the site or app. Every end is recorded with its reason.
  • Self-exclusion disconnects the player's active sessions immediately.
  • Forced closure (tab closed, app killed, device lost) is detected by a heartbeat from each open instance; ADM defines no interval.

What the platform builds

  • A server-side session service: the last counted event per session, the session ended at the time-out when no game session is open, every API call of an ended session refused.
  • A per-instance heartbeat. When no open instance has reported for the forced-closure interval, the session ends.
  • A player setting with server-side validation (1 to 59), and configuration for default, range, counted events and intervals.
  • One idempotent end-of-session method used by all causes, an append-only record of each end, and the PACG 6.32 disconnection with the receipt ID of the login's 6.12 sub-registration.
  • Game sessions are detached, not closed, when the user session ends; the same game session is reopened at the next login.

2. Rules

A. Inactivity time-out

  1. Maximum time-out of 20 minutes after the player accesses the gaming account; on inactivity the gaming and account-management functions are blocked. The player may set a different value, always below 60 minutes. Technical rules 2024 Part 2 ch. 1; Guidelines 2.1.14
  2. The verification checks that the default is not above 20 minutes, that a player-set value cannot go above 60 minutes, and that at the set value the user session ends with automatic disconnection from the site or app. The highest selectable value is therefore 59 minutes; lower values are allowed and ADM sets no minimum. Guidelines 2.1.14.1
  3. Default and allowed range are settings, not hard-coded. A fixed value stated only in the terms is not enough.
  4. Inactivity means no interaction of the player with the graphical interface of the site or the apps and no open game session. ADM does not list events and does not go down to mouse level. Any action the player takes on the interface (click, tap, key press, navigation, bet, game action) resets the timer; mouse movement alone is not needed. The list of counted events is configurable and documented in the technical report, and the lab tests what is described. Guidelines 2.1.14.1
  5. Passive events (window focus change, background polling, video playback) are not interactions. A scroll or touch-move on the page is a deliberate gesture on the interface and is counted in the default list. Guidelines 2.1.14.1
  6. An open game session counts as activity. Game sessions last at most 7 days (fixed-odds chance games and card games other than tournaments); skill games are out of scope. Close the game session when the player leaves the game, otherwise the time-out never starts. A live-casino table is a game session and counts. Guidelines 2.1.14.1
  7. A warning before the time-out is neither required nor forbidden by ADM. A click on the warning is an interaction. The warning must not stretch the limit: the time-out is counted from the last real interaction and the session ends at the limit. Guidelines 2.1.14.1
  8. No extra grace period is added for an app suspended in the background: a suspended app has no interaction, so the normal time-out applies. Guidelines 2.1.14.1
  9. The device or site signals to the player that the session ended; play resumes at the next login. Notices to the player are in Italian (technical terms excepted). Guidelines 2.7.7.1

B. End of the user session

  1. The user session starts at the player's login and ends when (a) the player logs out; (b) the time-out limit is exceeded; (c) documented conditions defined by the concessionaire require it; (d) the site or app is force-closed. ADM FAQ 12 March 2025 no. 38; ADM FAQ 17 April 2025 no. 28; Technical rules 2024 Part 2 ch. 1
  2. Forced closure covers closing the browser tab or window, killing the app, or losing the device. ADM prescribes no detection mechanism; each open instance sends a heartbeat (or keeps a live connection) and when no open instance has reported for a short, configurable interval the session ends. With several tabs the session ends when the last one stops reporting. (Should be checked with the partner: the interval is set with Netbet and validated with the lab.) Guidelines 2.1.14.1
  3. Every session end is recorded with its reason: logout, time-out, operator condition, forced closure.
  4. Self-exclusion disconnects the player's active user sessions immediately; account management stays reachable and started game activity is completed. A category-only self-exclusion closes the open game sessions of those categories only. Guidelines 2.9.4, 2.9.4.1; ADM FAQ 17 April 2025 no. 33
  5. ADM does not limit the number of parallel sessions; limit breach and self-exclusion speak of "all active user sessions". Ending the first session at a second login is allowed as a documented concessionaire condition. Guidelines 2.9.1.1; ADM FAQ 17 April 2025 no. 28
  6. Suspension or blocking of the account is a contract matter and fits case (c). Guidelines 2.9.5.1; Gaming account contract art. 14; PACG 7.2, 7.3

C. Interrupted rounds and game sessions

  1. When the user session ends and interrupts game activity, the interrupted activity is restored at the next login. The platform reopens the game session at login and does not force-close open rounds. Guidelines 2.1.15, 2.1.15.1
  2. For fixed-odds chance games the player cannot start a new round before completing the interrupted one; at reconnection the platform offers to complete it. After 7 days from the start of the user session the round counts as concluded and its result is still shown. Guidelines 2.1.15.1
  3. ADM game sessions are not tied to the user session. PGDA keeps the session open until the presumed end date given at opening, can extend it with message 810, and closes it with 500 or 700 when the table ends. The flow is in CHG-375326. PGDA 5.4.2, 5.4.3

D. PACG disconnection and time

  1. PACG 6.32 Disconnection tells the register about the logout of a gaming account and sends the balance at the same time. It carries the receipt ID of the sub-registration and user session being closed (ID Ricevuta Subregistrazione), the declared balance including bonuses and the bonus part. One disconnection is allowed per receipt. PACG 6.32; CHG-375899
  2. 6.32 is sent at logout and is a mandatory step in Sogei's test. (Should be checked with the partner: whether it is also sent on time-out or forced closure; self-exclusion and exceeded limits also cause automatic disconnection with a notice to the central system.) Guidelines 2.9.1, 2.9.4; ADM FAQ 12 March 2025 no. 38
  3. 6.32 retries follow PACG 2.1: 4 s for the first three retries, 10 s for the fourth and fifth, then every 30 s, with the same transaction ID. PACG 2.1
  4. Time means connection time: the interval between login and disconnection, whatever the device. Session time feeds the time alerts (CHG-375442) and the player's time limits (CHG-375322). Guidelines 2.9.1.1, 2.9.2.1; ADM FAQ 17 April 2025 no. 28
  5. All components use UTC and store session records in UTC. PACG fields typed DataOraUTC or OraUTC are in UTC; plain Data and Ora fields keep the older convention (CET with automatic summer time). The player display time zone is not regulated. Guidelines 2.1.5, 2.1.5.1; PACG 3, 6; PGDA 4.1
  6. Login: no "remember me" or cookie-based login that skips a step; every login goes through the steps in CHG-375899.

CheckResult
An open game session under its 7-day cap existsStay active (game session counts as activity)
Time since the last counted event is at least the time-outEnd the session, reason TIME-OUT
NeitherStay active, the timer keeps running

Time-out

StepWhat happens
1The player makes a counted event; the timer restarts from the full value.
2The time-out is reached and no game session is open.
3The session is ended with reason TIME-OUT; functions are blocked and the player is logged out.
4Any later bet or account change is refused: login required.

Forced closure

StepWhat happens
1Each tab or app instance sends a heartbeat every hb seconds.
2The last tab is closed, the app killed or the device lost.
3No instance reports for the forced-closure interval.
4Open game sessions are detached (round not closed).
5The end is recorded as FORCED_CLOSURE with times and instances; 6.32 follows where it is sent (rule 20).

4. Details, settings and codes

What the platform does

NeedDetail
Time-out and blockThe server keeps the last activity time per session. A reaper ends the session when now minus last activity reaches the time-out and no game session is open. Every API call checks the session state; an ended session answers 401 SESSION_ENDED with the reason.
Player settingStored per player (empty means default). Configuration: default 20, minimum 1, maximum 59. Server validation refuses 60 or more, zero, negative, empty and non-numeric values.
Counted eventsServer side, every authenticated request of a counted type updates last activity. Client side, listeners for click, tap, key and navigation report in the heartbeat. The list lives in one configuration and is exported as a table for the technical report.
Game sessionsA registry holds open game sessions (opened at casino launch, closed when the player leaves or the provider closes). While one is open and under its cap the session counts as active. A cap job closes sessions at 7 days.
Forced closureEach instance sends a heartbeat. The session ends when every instance is closed or silent for the forced-closure interval. A page-hide beacon marking an instance closed is an optimisation, not the rule. Several tabs share one session.
End of sessionOne method endSession(session, reason, subReason), idempotent; logout, time-out, operator condition and forced closure all call it. Append-only record: session ID, account, start, end, reason, sub-reason (self-exclusion, account state, concurrent login), instances, trigger.
Self-exclusionThe self-exclusion service publishes an event; the session service ends all sessions, or only the game sessions of the excluded categories, and pushes the end to every open instance.
RoundsOn end, game sessions become orphaned, not closed; the provider round is untouched. At the next login the registry offers to resume the same game session.
SecurityThe client clock is never trusted. Heartbeat and activity reports need the session token and are rate limited. An ended session revokes all its tokens; no refresh revives it.

Edge cases

CaseBehaviour
Bet request arrives just before the time-outIt is a counted event; the server processes it if it arrives before the session was ended, otherwise 401. A bet already accepted by ADM stays valid.
Throttled background tab, device asleep, offline for minutesThe heartbeat may be late; the interval tolerates a missed beat. After the interval the session ends; on return the client gets 401 and shows the end message.
Open game session and tab closedThe user session ends (forced closure); the game session is orphaned and the round untouched.
Two ends at onceThe first wins; the second call is logged and ignored.
Self-exclusion during a betA bet already sent to ADM completes; the next request is refused.
6.32 refused or timed outRetry with the same transaction ID; 1463 means already sent, mark done.

6. Screens

  • Profile, security: inactivity time-out in minutes (1 to 59) with the default in force shown; errors for out of range, empty or not a number; the allowed range read from configuration (maximum 59).
  • Warning dialog (optional): shown in every open instance before the end; the button counts as activity; ignoring it lets the time-out happen on schedule. On mobile a bottom sheet with full-width buttons.
  • Session ended page: the reason in plain words (time-out, forced closure, operator condition, self-exclusion, concurrent login); one login button; text in Italian. After self-exclusion the text points to support and responsible-gaming help.
  • Game screen: an open game holds the session; leaving the game closes the game session; after login a banner that the round was kept, when a round was kept.
