PSQF: fixed-odds sports betting

ADM's fixed-odds betting protocol (PSQF 5.2): event creation, bet sale, results and payment, result changes, odds errors, cash-out and accounting, with the message catalogue and return codes.

Use with the task CHG-375323. The task is the requirement. This kit adds reference detail for building and testing it: ADM rules with their sources, flows, messages and checks. If the kit and the task differ, the task prevails; if the task and ADM's protocol differ, the protocol prevails. A rehearsal PSQF bench with fake data runs the cases of this kit in the browser.

At a glance

  • Record first. Every bet goes to ADM in real time. The stake is debited only after ADM returns the ticket ID.
  • Two-step payout. Result, then payment to ADM (7900:2), then the credit to the gaming account (PACG 6.8). The balance moves only after both positive replies, and within one hour of the official certification of the result.
  • Offer. Only sports, competitions and bet types ADM has approved for Netbet. Each event is created with ADM before betting opens.
  • No cancel after acceptance. ADM refuses the cancel message for online bets. Cash-out is allowed, but not on bets placed even partly with bonus.
  • Corrections only through ADM. Wrong results and odds errors follow ADM's procedures. The platform never voids or re-prices a ticket on its own.
  • Stake, maximum win, system and payout rules are applied by the platform and are in the task CHG-375896. The sale 7900:6 carries prezzo and max_pag (maximum payment, boost included); the system sale 7900:7 carries prezzo and the base amount per system. How the platform works them out is in CHG-375896.

Rules

A. Official programme and offer

  1. Offer only the sports, competitions and bet types ADM has approved for Netbet. The official programme is built only from disciplines, competitions and bet types for which ADM has given prior approval, the acceptance programme is shown, and any complementary programme is sent to the central system before betting opens. Guidelines 3.1.4, 3.1.4.1
  2. The official programme is made from the disciplines, competitions and bet types ADM has authorised. It is the only document on which bets are accepted. Guidelines 3.1.4, 3.1.4.1
  3. PSQF gives the registry codes (7100 queries) and the authorisation lists: 5.9 authorised bet models and 5.15 authorised competitions. The mapping from Digitain markets to these codes is built by Netbet and Digitain. PSQF 5.4 to 5.9, 5.15
  4. Create each event with ADM before betting on it opens (7200:1). Create it from ADM's calendar (read with 7100:20, using ACC_AVV_CALENDARIO) or ex novo under an approved sport and competition; if ADM's calendar already has the event, the reply returns the calendar code. PSQF 5.10, 7.1
  5. A new event carries sport, competition, date and time, the two teams (ADM team codes, or a description where a team is not in ADM's list) and AVV_FEED_PROVIDER, the feed provider that generated it (table 14.29; 0 = concessionaire). AVV_FEED_PROVIDER is mandatory when the event is not accepted from the calendar. PSQF 7.1 p. 73, 13.53, 14.29
  6. Reply to 7200:1: an event in ADM's calendar returns 1024 with the calendar code. An event already created by an operator returns 6022 "Event already created", and INFO_AVV (mandatory in that reply) carries the programme and event codes. PSQF 7.1 pp. 72-74, 13.21, 14.30
  7. Markets and odds are not sent when the event is created. Bet types come from ADM's approved list. Only markets whose outcomes are built per event (outright winner, player lists) have their outcome list sent with 7200:3 before betting on them opens. Odds, and any line or handicap value, travel with each bet. PSQF 7.3, 8.1
  8. Keep the offer in line with registry and calendar changes. 7101:1 returns the last variation, 7101:2 a specific one. Variation attributes: INS_AVV_CAL (new calendar event), MOD_AVV_CAL (changed), ATT_DISATT_AVV_CAL (0 invalidates, 1 re-validates). PSQF 6.1, 6.2, 13.25 to 13.36
  9. Authorisation is also checked at sale: 3021 "Bet not authorised" and 3022 "Sport or competition not authorised". Approval is read with 5.9 and 5.15. PSQF 14.30, 7.1

B. Bet placement

  1. Every bet is sent to ADM in real time. It is accepted, and the stake debited, only after ADM returns the ticket ID. All checks that could reject the bet (limits, self-exclusion, risk, balance) run before sending. Guidelines 2.1.1.1
  2. 7900:6 sells single or multiple bets: up to 30 bets, one price. 7900:7 sells a system: up to 30 base events. Duplicate events, bets or outcomes in one ticket are refused (3005, 3016, 3017). PSQF 8.1, 8.2, 14.30
  3. The ticket ID is 80 bits, written as 20 hexadecimal characters. It is the unique code the bet screens show. PSQF 14.8; Guidelines 2.3.2
  4. ID_GIOCATA identifies the play: year, day of year and an identifier unique within the day per TAG. 3009 is the code for a play identifier that is not unique. A repeated ID_GIOCATA returns the existing ticket ID in ID_BIGLIETTO (13.47). PSQF 13.20, 13.47, 14.30
  5. PSQF is half-duplex: a client does not send while it waits for the reply to its previous request. A transaction is one request and one reply, identified by id_transazione. PSQF introduction, ch. 2
  6. No reply from ADM: resend the same request with the same transaction ID, after 2 s, then 4 s, then every 4 s, until a reply arrives. The bet is awaiting the reply meanwhile. The server returns the stored reply without reprocessing, for the last transaction of that client only. Two consecutive transactions must have different IDs. PSQF ch. 2
  7. The protocol sets no maximum wait: the client keeps sending until it has a reply for every message that changes data. When collection and play are prevented by an anomaly or a failed integrity check, the concessionaire informs the player and ADM and bears any full refund. PSQF 2; PSV 3; Technical rules Part 1 ch. 3
  8. For remote gaming a TAG is a process in a pool, at most 50 virtual terminals; 1540 refuses more. Each TAG carries one request at a time, so parallel bets need separate TAGs. PSQF 4.1 note, 14.30
  9. Messages are binary (fixed header, variable body, extended attributes), at most 4 KB each; the system-sale body is at most 2000 bytes. FIRMA_DIG01 is an MD5 digest signed with an RSA 256-bit key, PKCS1 padding, 44 base64 characters. IP_RISP gives the UDP port and IPv4 address for the reply. PSQF ch. 4, 4.3, 8.2, 13.19, 13.29
  10. Valid tipo_tag values for remote gaming: 5 Internet; 10, 11, 12, 14 desktop browser; 20, 21, 22, 24 desktop client; 30, 31, 32, 34 mobile site; 40, 41, 42, 44 smartphone app; 50, 51, 52, 54 tablet app. The last digit is the operating system (0 Android or Unix-like, 1 iOS or Apple, 2 Windows, 4 other); there is no 13, 23, 33, 43 or 53. A tipo_tag not enabled for the concessionaire returns 1522. PSQF 14.18, 8.1
  11. Odds have at most three decimals and are not below 1, except for composed bet types (DM 145/2022 art. 4 c. 2). INFO_QUOTA gives the representation: 1 hundredths, 2 thousandths. It is mandatory in requests 8.1 and 8.2, in the sale reply and in the 8.13 reply. Guidelines 3.1.5.1; PSQF 13.24, 8.13
  12. Live: a sale after the start time is accepted unless CHECK_INIZIO_AVVENIMENTO lists the events for which ADM must refuse once the start time has passed (3010). The sale reply flags events already in play in INFO_LIVE. A bet type is invalid, and the player refunded, if it is accepted between the actual start of the event and the start time in the official programme, or after one of its outcomes has already happened; . PSQF 13.13, 13.22, 14.30; DM 145/2022 art. 6 c. 3, art. 7 c. 1 lett. b
  13. Balance block: SALDO_CONTO in a sale is the account balance already reduced by the price and the bonus played. In payment, correction and cash-out messages it does not include the credit of the winnings; in the reversal (7900:12) the balance is not reduced by the amount to be reversed. CONTO_2 carries the gaming account. PSQF 8.1 to 8.3, 13.15, 13.50
  14. Bonus on a bet: ADM has three bonus types: 1 full win; 2 reduced win (payment = win minus bonus used); 3 win in bonus (telematic bets only, bonus used equals the stake). Bonus used on one bet is at most EUR 100. Header version 2 (FSC): BONUS_PREZZO in the sale and BONUS_PAG_RIMB in the payment and correction messages. Header version 3 (CFS): BONUS_PREZZO_2 and BONUS_PAG_RIMB_2. A wrong pair returns 3032. Bonus and bonus balance are sent split by game family (tables 14.27, 14.28) and the ADM bonus balance is reduced by that split. Guidelines 3.1.9; DD 167944/RU art. 2-4; PSQF 14.21, 13.54, 13.55
  15. Winnings boosts use boost types 2, 3, 4, 5, 6, 7 and 10 (percentage per event, fixed amount, per system, minimum number of events, tiered percentage), carried by: 2 MV_PERC_VAR; 3 MV_IMPORTO; 4 MV_PERC_VAR_SISTEMA; 5 MV_IMPORTO_SISTEMA; 6 MV_IMPORTO_VAR; 7 MV_IMPORTO_VAR_SISTEMA; 10 MV_FASCE (the sale 7900:6 accepts MV_PERC_VAR, MV_IMPORTO, MV_IMPORTO_VAR and MV_FASCE; the system sale 7900:7 accepts the three _SISTEMA ones and MV_FASCE; all optional); the events need flag_mv. 3012 refuses an invalid boost. PSQF 13.37 to 13.43, 14.13, 14.30
  16. No cancellation after acceptance: ADM refuses the cancel message 7900:3 for online bets (4004). After a cash-out the refusal is 4005. PSQF 8.4, 14.30
  17. Header and connection: the header version and the provider and concessionaire fields come from Netbet's connection and Sogei at set-up and are configurable. Version 2 carries the identifier of the connectivity provider (FSC), version 3 that of a service-provider concessionaire. The concessionaire code (cn) is in the header for the ticket messages 8.1 to 8.12; other services use "FSC/CFS,0,0,TAG". Keep-alive and integrity messages are described in CHG-375321. PSQF 4.1, 4.2

C. Bet screens

  1. Bet detail and bet history show at least the ADM ticket ID, the amount debited for each bet, the gaming account code and the player's tax code. The summary shows only the unique code from the central system as the bet code, with the debit amount, the account code and the tax code. Guidelines 2.3.2; Tender technical rules Part 1 par. 1.1 point 11
  2. The gaming account statement lists the receipt ID of each bet and covers at least the previous 30 days. Guidelines 2.9.19
  3. The site and apps are in Italian (technical terms of common use excepted) and show how malfunctions are handled. ADM prescribes no wording for refusal messages. Guidelines 2.7.3, 2.7.7

D. Results and settlement

  1. Send official results to ADM with 7200:16 (per bet status: RU result, AN void with zero winning outcomes) or 7200:17 for bets with additional information. Refunds and cancellations follow the PSQF messages (7200:11 time-window refund, 7200:14 outcome status). PSQF 7.6, 7.7, 7.11, 7.14
  2. A positive reply to the result authorises the later payment or refund message. ADM does not settle on its own: the platform sends 7900:2 per ticket, with importo = the actual amount to pay or refund. The reply returns the amount paid. Guidelines 2.1.2.1; PSQF 8.3
  3. After the positive PSQF reply, credit the account through PACG 6.8. The balance moves only after both positive replies. Guidelines 2.1.3.1; PACG 6.8
  4. Wins and refunds are credited within one hour of the official certification of the event that determines the win or refund. The hour does not start when Digitain sends the result or when ADM replies, unless a game-specific rule says otherwise (none found for fixed-odds betting). Tender technical rules Part 2 ch. 9; Guidelines 2.9.17, 2.9.17.1; Contract annex 6 art. 5, 12
  5. Win types: 1 win; 2 return as win; 3 half win and half return; 4 half return. A non-runner is outcome state N. Odds never fall below 1. PSQF 14.19, 14.4; Guidelines 3.1.7
  6. 3008 and 3018 belong to the sale group. The calculation rules the platform follows (truncation for single and multiple bets, dead heat) are in CHG-375896. PSQF 8.3, 14.30; Guidelines 3.1.6 to 3.1.8

E. Result changes

  1. A wrong result is corrected through ADM: delete it with 7200:9, then send the correct result; 7200:16 with tipo_op 0 modifies a result already inserted. PSQF 7.6, 7.9
  2. A collected ticket that becomes losing is reversed with 7900:12 (amount to reverse). A collected ticket whose amount changes is corrected with 7900:13 (importo = amount to pay or refund). The reversal is followed by PACG 6.9; after a correction, send the PACG credit (6.8) or reversal (6.9) for the difference. PSQF 8.7, 8.8; PACG 6.8, 6.9
  3. STORNO_NO_REF (13.44) allows reversing a collected ticket when the new result is not yet available, within one hour of the deletion of the wrong result. It cannot be used with MOD_LEGACY. TIME_STAMP_UTC (13.46) is mandatory in the replies of services 7100, 7101, 7200, 7900, 8003 and 8004; the 8000 and 8002 replies do not carry it. 5008 is the generic refusal; 5017, 5018 and 5022 are specific. PSQF 13.44, 13.46, 8.7, 14.30

F. Odds errors

  1. Odds errors go only through ADM's procedure. The concessionaire files through an application provided by ADM, outside PSQF, within three days after the last date communicated to the totalizer for the event. Later requests are inadmissible (irricevibili). Only bet types with a static outcome list qualify. Determination 172904/RU art. 2 c. 1, art. 3 c. 1 and 3
  2. The request states company and tax code, concession codes, event, programme and event code, bet type and code, additional-information value, all outcomes, the outcome and odds claimed in error, the other outcomes' odds and the time interval. Documentary proof is needed only for live (post-start) collection. Determination 172904/RU art. 3 c. 2
  3. ADM recalculates the win of each ticket registered at the totalizer in the declared interval. 8000:8 lists the tickets of a recognised request; request states are 1 processing, 2 not recognised, 3 recognised, 4 improcedibile, 5 rejected. STORNO_ERRORE_QUOTA (13.45) reverses a collected ticket while a request is processed. Determination 172904/RU art. 6 c. 4, art. 8 c. 4; PSQF 9.8, 13.45, 14.22
  4. While a request is processed ADM answers 5021 to payment, 5020 to cash-out and 5022 to reversal and correction. The platform never voids or re-prices a ticket on its own. PSQF 14.30

G. Cash-out

  1. Full cash-out is 7900:18 (id, importo_cashout). Partial cash-out is 7900:19: id, prezzo_cashout, importo_cashout, and the price and win amount of the new remaining ticket. ID_GIOCATA, FIRMA_DIG01 and CONTO_2 are mandatory for remote gaming. The Technical Rules and the guidelines (2.1.1.1, 2.1.3.1) require the account balance with the residual bonus in every account movement. The reply returns the id of the new ticket and a sequence number. 7900:20 gives cash-out information. PSQF 8.10 to 8.12
  2. Cash-out is not allowed on bets placed even partly with bonus (5019). It is refused with 5020 while an odds-error request runs. DD 167944/RU art. 3 c. 3; PSQF 14.30

H. Accounting, reconciliation, integrity

  1. Request ADM's accounting figures with the 8000 messages (platform advice: compare them with Digitain's own figures per accounting day). The daily statement is requested for a day given as year, month and day. What the platform displays is in CHG-375321. PSQF 9.1 to 9.9
  2. Every component of the concessionaire's system uses UTC as time reference. Guidelines 2.1.5
  3. 8004:1 keep-alive is sent every minute (CFS connection only). 8004:2 software integrity check is sent at least daily and again after every patch. Components (14.26): 1 gaming platform, 3 game acceptance system, 4 game system; each is identified by id_componente, version and hash_componente. A failed or impossible check is stored with its date and time; the component may keep running, and if the check fails again after 15 calendar days it is blocked. The concessionaire then asks for a specific technical conformity check. 8004 is sent by a CFS only. PSQF 12.1, 12.2, 14.26; Guidelines 2.1.13.1; ODV ch. 1
